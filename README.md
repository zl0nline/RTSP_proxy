# RTSP_proxy

План реализации единой точки доступа к RTSP-камерам через один внешний порт.

## Исходные условия

- центральный сервер уже маршрутизирует уникальные серые IP всех камер;
- сейчас каждой камере назначается отдельный проброшенный внешний порт;
- требуется заменить сотни портов единым адресом вида `rtsp://server:9999/<camera_id>`;
- учётные данные камер не должны передаваться клиентам.

## Целевая архитектура

```text
RTSP-клиент
    |
    | rtsp://server:9999/<opaque_camera_id>
    | RTSP over TCP (interleaved)
    v
MediaMTX
    |
    | sourceOnDemand
    v
rtsp://<private_camera_ip>/<stream_path>
```

Рядом с MediaMTX работает control service. Он не участвует в передаче видео, а:

- хранит или читает каталог камер;
- преобразует запись камеры в конфигурацию пути MediaMTX;
- синхронизирует добавления, изменения и удаления через Control API;
- ведёт аудит и предоставляет health/status API.

Для первого релиза все пути заранее синхронизируются из БД в MediaMTX. `sourceOnDemand: true` означает, что соединение с камерой устанавливается только при появлении зрителя. Это исключает гонку при первом RTSP-запросе и нормально масштабируется на 500–600 путей.

## Компоненты

1. **MediaMTX** — RTSP reverse proxy, единый внешний TCP-порт, on-demand источники.
2. **Control service (Go)** — синхронизация БД с MediaMTX, валидация, health API и метрики. Если у команды нет Go-экспертизы, до начала разработки следует отдельно сравнить поддержку Go и Python/FastAPI.
3. **PostgreSQL** — каталог камер и состояние синхронизации. Для PoC допустим SQLite, но логическая схема должна оставаться идентичной production-схеме, а миграции с первого дня проверяются на PostgreSQL.
4. **Prometheus-совместимые метрики и логи** — состояние источников, активные читатели, ошибки и время подключения.

## Модель данных камеры

- `id` — внутренний UUID;
- `public_id` — непрозрачный случайный идентификатор в RTSP URL;
- `camera_model` или `camera_type` — модель/профиль камеры для выбора RTSP path и диагностики;
- `private_ip` и `port`;
- `stream_path`;
- `camera_username`;
- `camera_password_encrypted` или ссылка на secret manager;
- `enabled`;
- `updated_at`;
- `sync_status` и `last_error`.

Секреты камер нельзя помещать в Git, логи или клиентские URL. Для PoC пароль шифруется AES-GCM, а ключ передаётся control service через переменную окружения и не сохраняется в репозитории или БД. Для production ключи и секреты переносятся в Vault/KMS либо аналогичный secret manager с ротацией и аудитом доступа. Внешние пользователи получают отдельные учётные данные либо токены с правом чтения конкретных путей.

## Этапы реализации

### 0. Проверка исходных условий

- составить перечень производителей, моделей и версий прошивок;
- выбрать хотя бы по одному экземпляру каждой модели/профиля и выполнить с сервера RTSP `DESCRIBE/SETUP/PLAY`;
- для каждой модели подтвердить TCP interleaved, on-demand подключение, повторное подключение и восстановление после обрыва;
- зафиксировать варианты RTSP path, особенности перелогина и способы передачи camera credentials;
- проверить firewall и доступность выбранного внешнего порта.

Критерий: сервер стабильно читает тестовые потоки напрямую по серым IP.

### 1. PoC MediaMTX

- запустить MediaMTX в контейнере;
- назначить RTSP-порт `9999`;
- описать 2–3 статических пути с `sourceOnDemand: true`;
- принудительно использовать TCP при подключении к источникам;
- проверить VLC и FFmpeg, параллельных клиентов и повторное подключение после обрыва камеры.

Критерий: все камеры доступны через один порт и разные `public_id`, дополнительные внешние UDP-порты не требуются.

### 2. Control service и БД

- создать схему БД и CRUD для камер;
- реализовать полную синхронизацию при старте и инкрементальные обновления;
- применять конфигурацию через MediaMTX Control API;
- валидировать IP, RTSP path и уникальность `public_id`;
- не допускать попадания паролей в логи и ответы API;
- добавить dry-run и отчёт о расхождениях.

Критерий: добавление или изменение записи в БД предсказуемо создаёт/обновляет путь без перезапуска видеосервиса; после рестарта MediaMTX полная синхронизация автоматически восстанавливает все пути из БД.

### 3. Авторизация и безопасность

- привязать Control API MediaMTX только к loopback (`apiAddress: 127.0.0.1:9997`) либо изолированной внутренней Docker-сети; порт API не публиковать наружу;
- настроить отдельную клиентскую авторизацию по путям;
- хранить camera credentials зашифрованно или в secret manager;
- ограничить входящий firewall портом RTSP и административным доступом;
- добавить rate limits/защиту от перебора на внешнем контуре;
- подготовить ротацию `public_id` и клиентских credentials.
- оценить RTSPS/TLS для публичного RTSP-порта; если клиенты его не поддерживают, ограничить доступ доверенной сетью/VPN и зафиксировать остаточный риск незашифрованного RTSP.

Критерий: клиент не видит адрес и пароль камеры и не может читать чужой путь.

### 4. Наблюдаемость и устойчивость

- health/readiness endpoints;
- метрики активных потоков, читателей, битрейта, ошибок и latency подключения;
- структурированные логи без секретов;
- backoff при недоступности камеры;
- graceful restart и резервное копирование БД;
- нагрузочный тест на ожидаемое число одновременных потоков.

Критерий: отказ камеры локализован, сервис восстанавливает поток после возврата камеры, оператор видит причину ошибки.

### 5. Массовая миграция

- подготовить идемпотентный импорт существующего реестра камер;
- сначала подключить 10 камер, затем 100 новых, затем остальные;
- оставить старые пробросы на период наблюдения;
- сравнить доступность и задержку;
- после подтверждения поэтапно убрать индивидуальные внешние порты.

Критерий: каталог полностью синхронизирован, клиенты переведены, старые пробросы удаляются без остановки сервиса.

## Проверки PoC

- два клиента смотрят один путь одновременно;
- несколько разных камер работают через один порт;
- камера отключается и возвращается;
- неверный `public_id` и неверная авторизация отклоняются;
- пароль камеры отсутствует в URL и логах;
- после рестарта control service и MediaMTX конфигурация восстанавливается;
- UDP с внешней стороны не требуется;
- измерены время первого кадра, CPU, RAM и входящий/исходящий битрейт.

## Решения для первого релиза

- не писать собственную реализацию RTSP-протокола;
- не ставить control service в медиапуть;
- не создавать путь по первому неизвестному запросу;
- синхронизировать все известные пути заранее, сохраняя источники on-demand;
- начинать с Docker Compose, затем при необходимости перейти к systemd или оркестратору;
- язык control service — Go: простой статический бинарник и удобная эксплуатация.
- окончательный выбор Go или Python/FastAPI подтвердить с учётом компетенций команды и долгосрочной поддержки до начала этапа 2.

## Открытые вопросы перед разработкой

- точные модели камер и варианты RTSP URL;
- требуемый способ клиентской авторизации: общий пользователь, пользователь на камеру или временные токены;
- ожидаемое число одновременных просмотров и средний битрейт;
- нужна ли запись либо только проксирование по запросу;
- источник текущего реестра камер и формат импорта;
- требования к высокой доступности и допустимое время восстановления.

## Предварительная оценка

- инвентаризация и проверка моделей камер: 1–3 рабочих дня в зависимости от разнообразия моделей и прошивок;
- PoC MediaMTX на представителях проверенных моделей: 1–2 рабочих дня;
- control service, БД, авторизация и базовая наблюдаемость: 4–7 рабочих дней;
- нагрузочные испытания и миграционные инструменты: 2–4 рабочих дня;
- production hardening зависит от требований к HA, секретам и архиву.

Оценка уточняется после этапа 0 и замера реальных камер.
