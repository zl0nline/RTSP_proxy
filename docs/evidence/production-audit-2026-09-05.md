# Аудит перед испытаниями на реальных камерах — 2026-09-05

Статус: **PRODUCTION NO-GO**. Это промежуточный отчёт аудита и прямой
диагностики источников, а не акт приёмки прокси. Пароли, полные RTSP URL,
ключи и адреса камер в отчёт не включаются.

## Проверенный контур

- Linux pilot: `grob`, установленный release `0.14.0`.
- Последний опубликованный на момент начала аудита commit: `1c5b962`.
- Его [CI run 33918579058](https://github.com/zl0nline/RTSP_proxy/actions/runs/33918579058)
  завершился успешно, включая native amd64/arm64 проверки. CI не заменяет
  испытания с реальными источниками и измерение ёмкости сервера.
- HTTPS readiness и страница входа на management LAN endpoint отвечали 200.
  Проверка выполнялась с сервера; доступ с отдельного компьютера локальной
  сети этим не доказан.
- Deep-probe production worker остаётся выключенным. Прямые диагностические
  подключения ниже не проходили через scheduler, broker или MediaMTX-ноду.

## Реальные источники

Для проверки предоставлено 12 камер. Секреты передавались диагностическому
процессу через stdin, не через аргументы команд. Сырой stderr медиаклиента
не публиковался: он может содержать URL с credentials.

| Проверка | Результат | Что это доказывает |
|---|---|---|
| Источник A: прямой ffprobe через RTSP/TCP | H.264, 1920×1080, exit 0 | Источник доступен для прямого чтения; не доказательство проксирования |
| Остальные 11: прямой ffprobe через RTSP/TCP | Истёк внешний deadline | Чтение не подтверждено; не классифицировать как «камера неисправна» |
| Источник A: DESCRIBE с авторизацией | 200, SDP H264/90000 | Basic-авторизация и описание потока работают |
| Остальные 11: DESCRIBE с авторизацией | Тайм-аут диагностического клиента | Требуется дальнейшее разделение несовместимости клиента, credentials и поведения камеры |
| Два представителя второй группы: первый DESCRIBE | 401 с Digest challenge | TCP и начальный обмен работают; 401 без credentials ожидаем |
| Те же два: новый TCP socket для авторизованного DESCRIBE | Снова тайм-аут | Одно лишь переоткрытие соединения не устраняет симптом |

Во второй группе пароль содержит буквальный `%`. В URL он кодируется как
`%25`, а при вычислении ответа авторизации используется исходный пароль.
Совпадение специального символа и Digest-авторизации пока не устанавливает
причину тайм-аута. Нужна контрольная проверка обычным RTSP-клиентом с теми же
данными. Подбор пароля не выполнялся.

## Найденные и исправленные дефекты

1. CLI смены локального пароля не обрабатывал ожидаемый отказ авторизации и
   нарушение политики нового пароля: вместо штатного сообщения был traceback.
   Добавлены регрессионные тесты и безопасное завершение с кодом 1. Неожиданные
   ошибки не маскируются под отказ авторизации.
2. `configure_camera_sources.sh` предлагал перезапустить несуществующий
   `rtsp-proxy-reconciler.service`. Исправлено на `rtsp-proxy@reconciler.service`.
3. Тот же скрипт принимал `.` и `..` как release ID и искал Python вне
   конкретного release directory. Теперь такие значения отклоняются до
   обращения к release; регрессия запускает настоящий shell-скрипт.

Проверка исправлений:

```sh
uv run pytest -q tests/test_operator_login.py tests/test_camera_secrets.py tests/test_linux_deployment.py
uv run ruff check src tests
uv run mypy src
```

Исправления в исходниках сами по себе не обновляют immutable release на
сервере. Для доставки нужен новый проверенный release и штатное обновление.

## Что остаётся до production

Порядок ниже — очередь исполнения, не список уже завершённых испытаний.

1. **Прямое чтение всех тестовых источников.** Разобрать зависание Digest-
   группы, проверить получение медиаданных и восстановление после обрыва.
   Нельзя считать успешный OPTIONS или SDP успешным чтением видео.
2. **Сквозной pilot через штатные API/dashboard.** Регистрация камеры с
   отдельными source credentials, применение конфигурации ноды, выдача grant,
   чтение через внешний порт. Подтвердить отказ второму читателю с RTSP 453
   и повторное подключение после освобождения первого. Не обходить RBAC/MFA
   прямыми изменениями БД.
3. **Изоляция изменений.** Во время непрерывного чтения менять состав ноды,
   добавлять вторую ноду, переносить камеру и менять порт выбранной ноды.
   Измерять разрывы на целевой и на незатронутых камерах; проверить обе ACL.
4. **Безопасность установки и восстановления.** Повторный/параллельный запуск
   и повреждённый source keyring теперь воспроизведены и исправлены в отдельном
   [проверенном кандидате](camera-source-bootstrap-safety.md): оба ревью и все
   девять заданий CI зелёные; отдельный root smoke тоже пройден. Полная
   привилегированная проверка нестандартных путей/environment и прерывания
   между заменами двух файлов остаётся открытой.
   Провести restore drill с БД и ключами, не только health rollback бинарника.
5. **Завершение Phase G.** Оставшиеся integrated special-range/alternate-protocol
   contracts, принятие ADR 0004,
   production broker/executor и periodic producer с durable health-state
   orchestration. Не включать незавершённую роль `probe` вручную.
   Explicit caller/shutdown cancellation уже проверена на обеих архитектурах:
   [результаты](phase-g-probe-cancellation.md). Реализованы политика периодических
   проверок и атомарное хранение состояния, но не готовый фоновый worker:
   [границы реализации](phase-g-routine-health-state.md). Короткая проверка рабочей
   камеры через отдельный медиапрокси также пройдена, включая 453 и добавление
   пути без разрыва; она не заменяет пункт 2:
   [результаты](phase-g-live-camera-media-smoke.md).
6. **Аварии и уведомления.** Отказ/возврат камеры, падение ноды и перезапуск
   сервера; одно уведомление об аварии и одно о восстановлении, без повторов
   и автоматического failover. Проверять через контролируемый SMTP-приёмник.
7. **Ёмкость и длительность.** Матрица 100 камер на ноду, увеличение числа
   нод на целевом железе, CPU/RAM/FD/сеть и запас ресурсов, затем 24-часовой
   soak. Двенадцать источников не доказывают ёмкость 100 камер или 50 нод.
8. **Admission.** Привязать evidence к точному commit, release и аппаратному
   профилю; обновить roadmap/issues по фактическим результатам. Production GO
   возможен только после закрытия обязательных gates и приёмки владельцем.

Нормативный перечень требований остаётся в
[production-плане](../PRODUCTION_PLAN.md#phase-g--probes-and-production-evidence).
