# Настройка ключей камер: повторный и параллельный запуск

Статус: исправления кандидата `0.15.2` прошли независимое ревью и финальный CI.
База изменения — `86ea930`. Schema остаётся 0023; production probe worker не
включается. Установленный pilot `0.14.0` на grob не изменён.

## Воспроизведённые дефекты

Изолированный запуск настоящего `configure_camera_sources.sh` показал:

1. Файл с JSON `{"broken":true}` принимался как исправный keyring, после чего
   изменялись environment-файлы. Скрипт проверял права, но не содержимое.
2. Два параллельных запуска проходили проверку отсутствия ключа. Второй успевал
   успешно создать ключ, а первый затем заменял его другим. Это способно сделать
   уже зашифрованные credentials нечитаемыми.

Начальный цикл: два падающих теста за 1,53 секунды. Повтор с проверкой фактической
замены ключа: два падающих теста и один успешный последовательный контроль за
2,49 секунды. Никакие реальные ключи, credentials или environment grob не читались
и не изменялись. Отдельный перебор гипотез не требовался: два повторных запуска
локализовали отсутствие проверки содержимого и межпроцессной блокировки.

## Исправление

- Один неблокирующий `flock` на сервер сериализует весь setup, включая разные
  пользовательские пути keyring. Конкурент получает безопасную ошибку с просьбой
  повторить команду. Файл блокировки не удаляется, чтобы не создать второй inode
  для конкурирующего захвата. Bootstrap явно устанавливает `util-linux`.
- После проверки существующих прав проверяются размер до 4096 байт, UTF-8, JSON
  и структура ключей через штатный `parse_camera_source_keyring` из установленного
  release. Содержимое и traceback не печатаются. Повреждённый файл не заменяется,
  environment не меняется; сообщение требует восстановить исходную резервную копию.
- Повторный последовательный запуск сохраняет ключ байт-в-байт.

## Проверка и границы доказательства

```sh
uv run pytest -q tests/test_camera_source_bootstrap.py --tb=short -rN
uv run pytest -q tests/test_camera_secrets.py tests/test_linux_deployment.py
uv run ruff check src tests
uv run mypy src
```

На Linux девять новых сценариев прошли за 6,46 секунды: повреждённые/пустые/
слишком большие данные, неверная кодировка, две разновидности параллельного
запуска, последовательный повтор и отсутствие `flock`.

Harness заменяет только фиксированные пути release Python и lock directory,
а root-only команды эмулирует во временном каталоге. Сам shell flow, Python,
парсер keyring, `flock`, `awk` и rename настоящие. Это доказательство порядка
операций и сохранности ключей, **не** привилегированный тест ownership или всей
иерархии нестандартных путей. Такие проверки, полный restore drill и отказ между
двумя заменами environment остаются отдельными задачами. Замена атомарна для
каждого файла, но не является общей транзакцией для WEB и reconciler.

Временный диагностический harness на grob перемещён в помеченный `debug`
каталог; постоянные регрессии находятся в `tests/test_camera_source_bootstrap.py`.

Дополнительно на grob выполнен изолированный root-прогон самого скрипта из
`6eddad9` с настоящим Python установленного `0.14.0`. SHA-256 проверенного
скрипта совпал с checkout: `ab21602e351b0775470beaec29bdb69ea9dad470795f41ff02e74304d9674a4e`.
Временные environment и keyring не связаны с рабочей конфигурацией. Пройдены:
создание с реальными `0640 root:rtsp-proxy-access`, сохранность ключа при повторе,
настоящая конкуренция за `flock`, отказ на повреждённом keyring без изменения
environment и успешный повтор после восстановления тестового файла. Это не
restore drill рабочих данных и не проверка всей иерархии пользовательских путей.
Тестовый каталог сохранён для диагностики; обычный lock-файл оставлен на месте.
После проверки установленные WEB/auth/collector/reconciler остались active,
`current` по-прежнему указывает на `0.14.0`.
